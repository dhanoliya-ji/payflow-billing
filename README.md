# PayFlow

**A multi-tenant subscription billing engine in .NET 10 — built so the ways billing
systems normally lose money are structurally difficult.**

[![CI](https://github.com/dhanoliya-ji/payflow-billing/actions/workflows/ci.yml/badge.svg)](https://github.com/dhanoliya-ji/payflow-billing/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![.NET 10](https://img.shields.io/badge/.NET-10.0-512BD4.svg)](https://dotnet.microsoft.com/)

PayFlow handles the full subscription lifecycle: plans with flat-rate, per-seat and
metered pricing; trials; proration on mid-cycle changes; invoicing; payment collection
through a gateway port; dunning with a configurable retry schedule; and reporting on all
of it.

Billing is an unusual CRUD problem because **its bugs are silent and they compound**. A
page that renders the wrong colour is noticed immediately. A system that drops a cent
per invoice, bills the same usage twice, or lets a cancelled subscription keep charging
is discovered weeks later by someone who now distrusts every number it has produced.
So the emphasis here is less on feature count than on making those failures hard to
write.

## Quick start

```bash
git clone https://github.com/dhanoliya-ji/payflow-billing.git
cd payflow-billing

# PostgreSQL and Redis (ports 55433 and 6380, so they don't collide with a local install)
docker compose up -d postgres redis

# A year of billing history, generated by running the real billing engine
# against a clock the simulator controls
dotnet run --project src/PayFlow.Seeder -- --reset --months 12

# API, dashboard and metrics
dotnet run --project src/PayFlow.Web
```

Then open **<http://localhost:8080/dashboard>**.

| | |
| --- | --- |
| Dashboard | <http://localhost:8080/dashboard> |
| OpenAPI | <http://localhost:8080/openapi/v1.json> |
| Health | `/health` (liveness) · `/health/ready` (database) |
| Metrics | `/metrics` — Prometheus text format |

Development API keys are in
[`appsettings.Development.json`](src/PayFlow.Web/appsettings.Development.json):
`pf_dev_acme_key` and `pf_dev_globex_key`.

```bash
curl -s http://localhost:8080/v1/analytics/mrr -H "X-Api-Key: pf_dev_acme_key" | jq
```

Everything else:

```bash
dotnet run --project src/PayFlow.Workers   # billing cycle, dunning sweep, outbox
dotnet test PayFlow.sln                    # 153 tests (Postgres must be up)
docker compose --profile app up -d --build # web + workers in containers
```

## Six decisions worth explaining

### 1. Money stores four decimal places, not two

A metered plan priced at **\$0.002 per API call** is a real thing to sell. Money rounded
to cents at construction stores that rate as \$0.00 and bills every call for nothing —
a bug this project shipped, caught by a test, and fixed by moving rounding.

Two decimals is a property of what a customer can be *charged*, not of every amount in
the system. `Money` carries four, and `Round()` is applied at exactly three boundaries:
invoice line amounts, invoice totals, payment amounts. Rounding is banker's rounding,
because away-from-zero biases a long run of half-cent amounts consistently upward.

### 2. Periods are half-open, and renewal is calendar arithmetic

`BillingPeriod` is `[Start, End)`. A period ending at midnight and the next one starting
at the same instant do not both contain it, so usage recorded exactly on the boundary is
billed once rather than twice.

Renewal uses `AddMonths`, which clamps: a subscription starting **31 January** renews 28
February, then 31 March. Adding 30-day blocks instead walks the anniversary earlier
every year — the classic subscription-billing bug.

### 3. The tenant comes from the credential, never from the request

The original implementation read an `X-Tenant-Id` header and fell back to a hard-coded
tenant when it was missing:

```csharp
var id = Guid.TryParse(tenant, out var parsed) ? parsed : Guid.Parse("11111111-...");
```

Any caller could read any tenant's billing data by sending a GUID. Now the tenant is
derived from an API key the caller proves it holds, compared in fixed time; missing and
wrong keys are rejected identically, because distinguishing them confirms whether a
guessed key belongs to someone.

### 4. Declines are a normal outcome, with a policy

Most failed subscription revenue is not customers leaving — it is expired cards and
temporary declines. `DunningPolicy` is a value object, not a constant: retry offsets
widen (1, 3, 5, 7 days), because retrying minutes later mostly reproduces the decline
and counts against the merchant's retry allowance. Permanent declines — expired,
blocked, stolen — are written off immediately rather than consuming the schedule.

Failed attempts are stored as rows. A system that records only successes cannot explain
where revenue went.

### 5. There are four distinct ways to double-bill, so four mechanisms

| Risk | Mechanism |
| --- | --- |
| Metering agent retries a report | Client idempotency key, enforced by a **unique index** — not a read-then-write two concurrent retries can both pass |
| Worker crashes after charging, before committing | Charge key derived from invoice + attempt, so the replay returns the original capture |
| Billing cycle runs twice | An existing invoice for the period blocks a second |
| Two runs allocate one invoice number | `INSERT … ON CONFLICT … RETURNING`; `SELECT MAX(number)+1` hands both the same number |

### 6. The analytics are computed independently of the code that wrote the data

If revenue and churn are computed by the same code that produced the rows, a bug is
invisible — the report agrees with the database because both are wrong the same way.

[`analytics/payflow_analytics.ipynb`](analytics/payflow_analytics.ipynb) reads
PostgreSQL directly and recomputes everything from the stored ledger. Its last two cells
are **assertions, not illustrations**: zero cross-tenant references, and contiguous
per-tenant invoice sequences. On the seeded database both hold.

## Analytics

The seeder replaces `IClock` with one it drives and steps a day at a time through a
year. Its only inputs are signups, usage, cancellations and plan changes — every
invoice, retry and write-off is `BillingCycleService`'s own output. A billing bug shows
up as a wrong curve instead of being hidden by fixture data. Runs are reproducible: the
same `--seed` gives the same history.

A 12-month, 60-customer run produces roughly:

| | |
| --- | --- |
| Subscriptions | 88 — 60 active, 14 voluntarily cancelled, 13 expired through exhausted dunning |
| Invoices | 213, \$23.2k collected, \$2.2k written off |
| Dunning recovery | 88.7% → 44% → 30% → 0% across the four attempts |

```bash
pip install -r analytics/requirements.txt
jupyter notebook analytics/payflow_analytics.ipynb
```

The notebook is committed **with its outputs**, so the charts are readable on GitHub
without running anything.

## Project layout

```text
src/
  PayFlow.Domain/          entities, value objects, state machine, proration — no dependencies
    Common/                Money, TenantId, Entity, Guard
    Plans/ Subscriptions/ Invoicing/ Payments/ Usage/ Billing/ Events/
  PayFlow.Application/     use cases and the ports they need (IClock, IPaymentGateway, …)
  PayFlow.Infrastructure/  EF Core, migrations, gateway simulator, outbox, idempotency
  PayFlow.Web/             API, auth, dashboard, metrics
  PayFlow.Workers/         billing cycle, dunning sweep, outbox dispatcher
  PayFlow.Seeder/          generates history by running the real engine on a fake clock
tests/
  PayFlow.Domain.Tests/       124 unit tests
  PayFlow.Integration.Tests/  29 tests against real PostgreSQL
analytics/                 the notebook
docs/                      problem statement, objectives, architecture, API
deploy/                    Dockerfiles, Terraform starter
```

Dependencies point inward; `PayFlow.Domain` references nothing. The one deliberate
compromise — the application layer referencing EF Core for `IPayFlowDbContext` — is
argued in [architecture.md](docs/architecture.md#the-one-deliberate-compromise).

## Testing

```bash
docker compose up -d postgres
dotnet test PayFlow.sln
```

**124 domain tests** over the rules that carry money: rounding and sub-cent unit prices,
calendar arithmetic across month ends and leap years, the full subscription transition
table (including that *no* transition leads out of a terminal state), proration,
invoicing, and dunning schedules.

**29 integration tests** against real PostgreSQL. Not an in-memory provider: the first
attempt used SQLite and it could not translate the billing cycle's central query — a
comparison against a member of a complex type — which Npgsql handles without trouble. A
suite that cannot execute the one query the whole cycle depends on is not testing the
cycle. Running the migrations in the fixture also puts the migration SQL under test.

CI additionally runs the seeder and executes the notebook end to end, and fails if the
EF model has drifted from the migrations.

## Configuration

Standard ASP.NET Core configuration — `appsettings.json`, environment variables, user
secrets.

| Key | Purpose |
| --- | --- |
| `ConnectionStrings:Postgres` | Required |
| `ConnectionStrings:Redis` | Optional — falls back to an in-process cache |
| `Authentication:Tenants` | Tenant id, name and API key per tenant |
| `Authentication:AllowAnonymousDevelopmentTenant` | Development only; the host refuses to start with it on elsewhere |
| `PaymentGateway:*` | Simulator success rates and seed |
| `Workers:*` | Billing, dunning and outbox intervals |

Environment variables use the double-underscore form:
`ConnectionStrings__Postgres=Host=…`.

## Known gaps

Stated rather than implied:

- **The payment gateway is a simulator.** There is no real processor integration.
- **No tax engine.** `Total` is kept distinct from `Subtotal` so adding one later does
  not change the meaning of any stored column.
- **API keys are compared against configuration.** In production only a hash should be
  at rest, in a secret store.
- **The outbox dispatcher logs** rather than publishing to a broker. Swapping it is a
  change to one method.
- **No rate limiting.**
- **Multi-currency is per customer, with no conversion.** A tenant's MRR across mixed
  currencies is not a single number, and the analytics assume one.
- **The Terraform starter** has no VPC, subnet group or secret management.
